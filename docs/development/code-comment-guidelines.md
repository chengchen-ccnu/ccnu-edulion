# 代码注释与人工可读性规范

## 1. 目标

代码首先要靠清楚的命名、较小的方法和明确的模块边界表达含义，注释用于补足人工阅读时无法仅从语句直接看出的业务信息。最低目标是让后续开发者无需重新推演整条调用链，就能回答：

- 这段代码负责什么，不负责什么；
- 输入从哪里来，代表什么，允许哪些范围或空值；
- 返回什么，或者会把系统状态改成什么；
- 会写入哪些数据库、缓存、MQ、OSS 或外部系统；
- 为什么要这样处理，失败、重复调用和重试时会发生什么。

禁止为了“注释数量”逐行翻译代码。`count++ // 数量加一` 之类注释没有信息价值；权限边界、幂等键、状态转换、重试上限和不能删除某段逻辑的原因才是重点。

## 2. 必须添加注释的位置

| 位置 | 最低说明内容 |
|---|---|
| 业务类、接口、服务、Worker | 职责、边界、主要协作者和不负责的内容 |
| 公共方法、API 适配方法 | 功能、输入、输出、异常、权限和副作用 |
| 复杂私有方法 | 算法/业务目的、关键前置条件和结果；简单委托方法可省略 |
| 状态机、幂等、重试、补偿、锁 | 状态变化、重复调用语义、上限、失败去向和选择原因 |
| MQ 生产者/消费者 | 事件类型和版本、输入信封、ACK 时机、幂等键、重试/DLQ 行为 |
| 数据库事务、复杂 SQL、Flyway | 所属领域、事务边界、约束/索引原因、迁移目的和不可逆影响 |
| OSS/文件处理 | 输入资产用途、对象状态、输出派生文件、临时文件与清理规则 |
| Python Agent 节点、工具、检索器 | 状态输入、状态输出、模型/检索调用、副作用和终止条件 |
| Vue 页面、共享组件、composable | 页面/组件职责、角色边界、关键 props/emits、数据来源与错误状态 |
| OpenAPI、事件 Schema、配置 | 字段业务含义、单位、范围、枚举语义、默认值和安全风险 |
| 复杂测试 | Given 输入/前置状态、When 操作、Then 预期结果和覆盖风险 |

自动生成的 OpenAPI 客户端、`schema.d.ts`、`target`、`dist`、第三方代码和纯框架样板不手工补注释。生成代码缺少说明时，应回到 OpenAPI/Schema 的 `description` 或生成源补充。

## 3. 各技术栈写法

### 3.1 Java

业务类和重要方法使用 Javadoc。至少写清功能、参数业务含义、返回结果；有明确异常或副作用时增加 `@throws` 和正文说明。

```java
/**
 * 确认浏览器已经把文件直传到 OSS，并创建后续处理任务。
 *
 * <p>输入的 uploadId 必须属于当前用户；本方法会向 OSS 复核对象大小和 ETag，
 * 在同一数据库事务中更新媒体状态并写入 Outbox，但不会在请求线程中执行转码。</p>
 *
 * @param uploadId media-service 创建的上传会话 ID
 * @param request 客户端提交的分片 ETag 和幂等请求号
 * @return 确认后的媒体 ID、当前处理状态和可查询状态的地址
 * @throws MediaValidationException 对象不存在、大小不符或上传会话无权访问时抛出
 */
MediaConfirmation confirmUpload(UUID uploadId, ConfirmUploadRequest request);
```

不要给每个构造器注入字段写“这是某某服务”之类注释。类级职责和准确命名能够说明的内容不重复。

### 3.2 Python

模块、公共类、公共函数、Agent 节点和工具使用中文 docstring，并保留类型标注。

```python
def rerank_candidates(query: str, candidates: list[Document]) -> list[Document]:
    """对混合检索候选进行重排并截断。

    Args:
        query: 学生的当前数学问题，不包含会话历史。
        candidates: 关键词和向量召回合并去重后的候选文档。

    Returns:
        按相关度从高到低排列、且不超过配置上限的文档列表。

    Raises:
        RerankerUnavailableError: 重排模型不可用且未配置降级策略时抛出。
    """
```

Agent 节点还要说明读取和写回哪些状态字段，以及何时终止或转入人工帮助。

### 3.3 TypeScript、Vue

API 封装、共享函数、composable、复杂组件和路由守卫使用 TSDoc/JSDoc。页面文件在脚本区说明角色、数据来源和主要交互；props、emits 或状态含义不直观时单独说明。

```ts
/**
 * 轮询媒体处理状态，直到资源就绪、失败或超过页面等待上限。
 * @param mediaId 已完成上传确认的媒体资产 ID。
 * @returns 最终状态；超时返回最后一次状态，不会取消后端转码任务。
 */
```

模板中的普通按钮、循环和条件渲染不逐行注释；复杂权限分支和兼容迁移逻辑需要说明原因。

### 3.4 SQL、YAML 和契约

- 新建 Flyway 文件应在开头说明迁移目的、所属服务、创建/修改的表以及是否可逆；复杂索引、唯一约束和状态检查约束说明业务原因。已经在任何环境成功执行的迁移属于不可变发布物，不得为了补注释回写文件；其缺失说明应放到所属持久化包的 `package-info.java`、交付文档或后续向前迁移，避免改变 Flyway checksum。
- OpenAPI 的操作、请求、响应、字段、枚举和单位优先用 `summary`/`description` 表达，生成客户端继承这些说明。
- 事件 Schema 说明生产者、消费者、触发时机、幂等键、版本兼容和敏感字段限制。
- 环境变量说明用途、安全级别、默认关闭/开启原因，禁止把真实值写进注释。

## 4. 人工检查清单

每个任务交付前逐项确认：

- 新增或修改的业务类是否一眼能看出职责和边界；
- 重要方法是否说明功能、输入和输出；
- 数据库、Redis、RabbitMQ、OSS、文件系统或外部 API 副作用是否明确；
- 权限、幂等、状态机、重试和失败终态是否说明“为什么”；
- 注释是否与实际分支、异常和返回值一致；
- 是否误给生成代码、getter/setter 或显然语句添加了冗余注释；
- 是否在注释中泄露凭据、签名 URL、隐私或真实业务数据；
- 交付文档是否记录本任务的注释覆盖和仍未解决的可读性问题。

截至 2026-08-02，T01～T07 已合并代码在实施时没有从任务开始就统一强制执行上述注释规范。独立分支 `codex/t01-t07-comment-audit` 已完成集中人工审计：补齐 Gateway/IAM/课程核心事务与权限链路、Python Agent 状态机和检索、三端认证与复杂课程页面、Flyway 关键约束、OpenAPI 操作和媒体事件信封说明；T07 已有的 Outbox、消费幂等、有限重试/DLQ、OSS、转码和回收说明经调用链复核后保留。自动生成客户端、框架启动类、简单 DTO/getter/setter、纯样板和自解释测试仍有意排除，不以逐行注释作为完成标准。

处理顺序固定如下：

1. **T08 开始前集中治理 T01～T07（已完成，待审计 PR 合并）**：独立分支 `codex/t01-t07-comment-audit` 从包含 T07 PR #9 的最新 `main` 完成可读性审计，只补充/修正注释、契约描述和审计文档，没有改变业务行为；后续风险记录在 `docs/delivery/T01-T07-comment-audit.md`。
2. **不回到旧任务对话逐个修改**：旧分支已合并或删除，旧对话基于过期代码。分散补注释容易冲突、遗漏并产生多份难审查 PR。
3. **T08 及以后随任务维护**：每个任务负责新代码和被触及旧代码的注释质量；未触及的大范围历史文件由集中审计任务处理。

不建议等全部功能完成后再一次性补注释。届时上下文丢失、行为已经多次演进，最容易出现看似完整但内容错误的注释。
