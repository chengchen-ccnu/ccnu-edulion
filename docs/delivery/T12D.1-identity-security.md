# T12D.1 unique identity, protocol and verification security delivery

## 目标与边界

T12D.1 先把外部契约从 OpenAPI 0.17.0 向前演进到 0.18.0，再实现 IAM、Gateway、Redis、标准 SMTP 端口和生成客户端。正式与测试环境只允许已验证邮箱或中国大陆手机号登录；昵称必填、允许中文和重名，内部 `account` 只由服务端生成。任务没有实现 T12E Vue 页面、真实短信供应商、账号注销、人工申诉、反馈提交或“记住我”。

现有会话架构保持不变：Access JWT 默认 15 分钟并只在页面内存保存；Refresh Token 由 7 天 HttpOnly Cookie 持有，MySQL `refresh_session` 是设备和撤销事实；Redis 只保存短期 CAPTCHA、验证码、冷却、失败/锁定、限流和 `sessionVersion`，不保存完整 JWT 或完整 Session。

## 主要架构与安全流程

- 身份规范化：邮箱去首尾空格并以小写唯一保存；手机号只接受中国大陆 11 位形式并保存为 `+86` E.164。每账号由数据库约束保证最多一个已验证邮箱和一个已验证手机号。
- 密码登录：仅按已验证身份查询，昵称和历史 `account` 始终拒绝。前三次错误不需要 CAPTCHA；第 4、5 次先一次消费 CAPTCHA，CAPTCHA 错误不执行密码校验、不增加密码失败数；第 5 次密码仍错后锁定 15 分钟并返回 429/`Retry-After`。未知身份执行等价外部响应和虚拟密码校验。
- 验证码登录：注册、找回密码和验证码登录的发送入口必须先消费约两分钟的 Redis 算式 CAPTCHA；验证码登录只允许已有 ACTIVE 账号，不自动注册。验证码和目标只以 HMAC 摘要进入 Redis，答案不进入响应、日志或 MySQL。
- 发送端口：`VerificationDeliveryPort` 隔离供应商，local/test 使用固定码，生产邮箱使用标准 SMTP。发送失败会删除本次挑战/冷却以允许安全重试；`.invalid` 地址始终拒绝 SMTP。生产无短信能力时渠道能力接口关闭手机注册和手机验证码登录。
- 身份状态机：查询仅返回脱敏值和 revision。绑定需要当前密码与新身份验证码，新增第二身份撤销其他设备；换绑先验证后在事务中原子替换；解绑禁止删除最后身份。换绑/解绑撤销全部设备。三种变更均记录安全审计、递增持久 `sessionVersion`，并以 `expectedRevision` 和 `clientRequestId` 提供 409 冲突及幂等重放。
- 协议：`protocol_document` 保存类型、不可变版本、正文、生效时间、当前标记和重新同意要求；注册必须提交当前有效 TERMS 与 PRIVACY 版本。local/test 正文显式标记“不可用于正式发布”。
- Cookie 隔离：身份变更需要识别当前 Refresh Session，因此 `EDU_REFRESH` Path 收口为 `/api/v1`。Gateway 仅向 IAM 路由保留它，转发其他领域前精确剥离该 Cookie；其他普通 Cookie 不受影响。

## API 与生成客户端

主要新增或收口的 API：

- `POST /api/v1/auth/captchas`、`POST /api/v1/auth/captchas/{captchaId}/refresh`
- `GET /api/v1/auth/channel-capabilities`
- `POST /api/v1/auth/verification-login-challenges`、`POST /api/v1/auth/verification-login`
- `GET /api/v1/protocols/current`
- `GET /api/v1/users/me/identities`
- `POST /api/v1/users/me/identity-verification-challenges`
- `POST /api/v1/users/me/identities`、`PUT/DELETE /api/v1/users/me/identities/{identityType}`

密码登录请求字段由 `account` 收口为 `identity`；注册由服务端生成内部账号并接收 1～30 个可见字符的 `displayName`。`web-apps/packages/api-client/src/generated/schema.d.ts` 已由同一 OpenAPI 生成；共享登录表单只做既有字段适配和邮箱/手机号文案，没有新增 T12E 路由或页面。

## 本地配置、Seed 与清理

所有本地秘密只经 `scripts/Invoke-WithLocalEnvironment.ps1` 注入。真实 SMTP 凭据使用 `scripts/Initialize-LocalSmtp.ps1` 交互写入当前 Windows 用户可解密的 DPAPI 文件；脚本和应用不得读取到控制台、写入仓库或明文 `local.env`。续验修复了该初始化脚本在 Windows PowerShell 5.1 下的未初始化变量问题，并改为复用既有发件地址、临时文件原子替换配置。本轮通过包装脚本在允许外网的本机环境启动 IAM/Gateway，真实 SMTP 两次投递均返回 202 并由操作者确认收件；文档、日志和仓库不记录完整收件地址、SMTP 用户名、密码、授权码或验证码。

local/test Seed 幂等创建以下已验证身份，且绝不向其发送 SMTP：`student1@example.invalid`、`teacher1@example.invalid`、`teacher2@example.invalid`、`admin1@example.invalid`。内部 account 由 Seed 固定为技术标识但不能登录；Seed 同时创建当前 local/test TERMS、PRIVACY 正文，正文明确不可正式发布。

清理前必须确认目标是专用 IAM dev/test Schema，再执行 `java-platform/iam-service/src/main/resources/db/seed/cleanup-iam-seed.sql`。脚本仅按四个固定 user ID 及外键逆序清理，不按邮箱后缀或全表范围删除；重建时显式设置 `IAM_SEED_ENABLED=true` 和未跟踪的 `IAM_SEED_PASSWORD`，经安全包装脚本重启 IAM。生产 profile 不加载 Seed。

## 人工演示

1. 查询渠道能力和当前 TERMS/PRIVACY，确认未配置生产短信时手机发送入口关闭，协议正文与版本来自服务端。
2. 创建 CAPTCHA，确认响应只有算式题和 ID；答错不增加密码失败数，答对后不可重放。
3. 使用已验证邮箱或手机号进行密码/验证码登录；对未知身份比较响应形状并确认未创建账号。
4. 登录后查询脱敏身份，以当前密码、新身份验证码和 revision 绑定第二身份；检查其他设备撤销。再换绑或解绑，确认全部设备撤销、旧 revision 返回 409、最后身份不可解绑。
5. 在 local/test 启用 Seed，确认四个 `.invalid` 邮箱可登录但 SMTP 适配器拒绝投递；执行精确清理脚本并重新启用 Seed 验证幂等重建。

## 风险与后续依赖

- 真实 SMTP 续验已经闭环：算式 CAPTCHA、邮件挑战、人工收件、错误次数、正确消费、重放拒绝和真实注册均通过。旧模板被人工指出“用途：注册”过于机械且未说明有效期，已最小修复为按业务目的生成自然语句，并从配置读取 10 分钟 TTL 写入正文；第二封真实邮件由操作者确认发件显示、用途、有效期、一次性提示和正文全部正确。过期拒绝由真实 Redis 5ms TTL 用例验证。临时账号、身份、协议同意、注册幂等事实、安全审计、两条临时协议和精确 Redis Key 均清理为零；未产生 Refresh Session，未修改或删除 Seed。
- 本轮发现并修复 Gateway 未公开放行 T12D.1 CAPTCHA、验证码登录挑战/提交、CAPTCHA 刷新、渠道能力和当前协议端点的问题；修复保持在现有分支，未扩展到 T12E 或真实短信供应商。

- T12E 只能消费 0.18.0 生成客户端实现页面，不能复制 DTO 或放宽安全状态机。T17A 再处理已登录用户的强制重新同意交互；T12H 单独设计账号注销。
