# T17C.3 管理员邀请与受邀开户前端

2026-10-22，分支 `codex/t17c3-admin-invitation-web`；开工工作区干净，保留总控规划 `901278d`，基线 `main@1121dce`。实现、自动化、受控真实发信/收件/开户及精确清理已完成，等待总控独立验收；Git交接见文末。

## 目标与边界

只交付既有账号权限区内邀请创建、已知ID单项查询、发送与接受两维状态、有限重发，以及student-web唯一身份壳中的公共 `/accept-admin-invitation`。两项侧栏仍为教师审核、账号权限，默认管理落点仍是教师审核。没有邀请全量列表、邮箱检索、公开管理员注册或另一套登录。

没有修改Java、OpenAPI0.31.1、事件或数据库迁移，没有重复DTO。`schema.d.ts`由唯一OpenAPI生成，新增类型只是生成schema的别名。

## 主要文件与调用流程

- 管理端 `views/AccountUsersPage.vue` 在同一路由切换原账号页与 `AdminInvitationPanel.vue`，每个面板独立清理请求/内存；原账号操作和权限边界保留。
- `admin-invitations-api.ts` 通过共享认证的一次401恢复调用生成GatewayClient。`AdminInvitationPanel.vue`保存原clientRequestId和载荷，创建/重发45秒、查询15秒有界等待；未知结果最多三次手动精确重放，不能换ID或另建邀请。未知结果、邮箱或理由草稿有离页/关闭提示，刷新/崩溃后不承诺恢复原载荷。
- 共享身份包扩展 `sanitizeAccountPermissionsQuery`：`panel=invite`不需要userId，只保留合法invitationId；移除账号/命令/分页/敏感或重复参数及hash。原detail/coordination白名单不放宽。`buildAdminInvitationAcceptanceUrl`从既有student-web配置构造无查询/片段的通用地址。
- 学生端 `AcceptAdminInvitationPage.vue` 复用AccountFrame；ID/邮箱/43字符URL安全凭证手动输入。昵称1～30可见字符、密码至少12字符且UTF-8最多72字节；确认密码只在前端。路由守卫剔除所有查询/片段，不读取邀请信息，也不自动恢复另一账号会话。已知已登录时阻止开户，提示退出或独立浏览器上下文。
- `admin-invitation-api.ts`直接调用公开accept，明确 `credentials: omit`，不附Authorization、不调用登录/刷新。201后清除全部表单，展示已开通并提供统一 `/login`。无效/过期/未发送/已用422保持统一提示；409不引导转换账号。只对昵称/密码给固定安全字段说明，不回显服务端任意秘密验证原因。
- accept没有幂等请求ID。网络/5xx/45秒超时/取消进入“结果未确认”，清除秘密并锁住本页再次提交，给正常登录及联系邀请人查询的路径，不通过再次422断言首次失败。
- 共享 `createRequestScope` 只提供超时和中止；取消立即清超时定时器，不能证明后端回滚。两个页面隐藏/离线/卸载取消HTTP，管理员身份变化或401/403清私有状态，旧查询代次不能串到新邀请。

| 已有接口 | 页面行为 |
|---|---|
| POST `/api/v1/admin/invitations` | 邮箱规范化、10～500字理由、确认、稳定请求ID；202只表示回执 |
| GET `/api/v1/admin/invitations/{invitationId}` | 只按已知非秘密UUID读取单项脱敏事实；404不证明原创建未提交 |
| POST `…/{invitationId}/resend` | 当前expectedRevision、理由及确认；60秒冷却、六次上限由服务端裁决，重发废旧凭证并重起24小时 |
| POST `/api/v1/auth/admin-invitations/accept` | 匿名正文一次性开户，201仅返回userId，无会话 |

发送PENDING/SENT/FAILED与接受AWAITING/EXPIRED/ACCEPTED独立展示；SENT只表示SMTP接受，不能证明收件箱投递或已开户。PENDING默认2秒最多30次查询（props有界可调），到限手动刷新，不后台发信。409要求重新查询，再由操作者决定重发；429按Retry-After阻止请求，不自动重试。隐藏/离线后手动恢复查询。

## 验收数据与精确清理

create创建一临时管理员、一普通账号，均为 `t17c3_<UUID>` / `@example.invalid` 合成身份；先记录UUID再写库，重复create复用清单。只复用user/user_role/user_identity，真实邀请/命令/安全审计/开户账号由正常Gateway→IAM调用产生，登录产生本轮refresh_session/login_audit及精确Redis会话/风控Key。真实受控邮箱由用户提供，不进入交付文档或脚本固定值。

cleanup先校验清单账号技术前缀，只通过本轮invited_by UUID定位邀请及accepted_by；按邀请ID/操作者/用户ID事务删除邀请命令、邀请、本轮安全审计/会话/身份/角色/账号。事务前保存无秘密UUID清理计划，SQL已提交后Redis失败仍能恢复accepted_by定位；成功后才删除计划。Redis只删除本轮用户精确会话版本/账号风控键及Gateway用户维度发信限流键，不删除共享IP限流。前后比对原管理员、存量课程/题库/历史五域Outbox；不全表清理、FLUSHDB、purge或修改《线性代数》。清理后删除活动清单和临时DPAPI；重复cleanup幂等，需重建时重新create。

最终实际：两个初始合成账号、一封邀请（创建及一次重发两个命令）、一个真实接受的新管理员，以及关联安全审计/登录/刷新会话/Redis精确键均已清理。cleanup和重复cleanup通过，临时DPAPI与活动清单已删除；Gateway用户发信键另行精确复查为不存在。原管理员、手工课程及存量题库、历史五域Outbox比对一致。仅保留忽略目录`.m2/t17c3-browser`的验收截图/无秘密定位与结果；所有本轮Java/前端/Mock/Prism进程已停止，相关端口无监听。邮件仅发送两封，用户均确认收到；邮件发送不可撤回，即使数据库精确清理也不会撤回已发送邮件。
