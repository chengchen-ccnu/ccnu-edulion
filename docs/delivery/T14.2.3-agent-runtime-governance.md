# T14.2.3 Redis 运行治理与 Agent 真实链路交付计划

日期：2026-09-10。状态：前置审计通过，规划分支已准备，尚未实现业务代码。

## 任务目标

在不改变 Agent Access 作为会话事实源的前提下，为真实多实例运行补齐短期协调能力，并完成 Java Agent Access 到 Python 动态 Agent 的真实 SSE 验收：

1. Redis 管理有 TTL 的执行租约、取消标记、最近运行安全元数据，以及用户跨会话并发和分钟/日额度。
2. MySQL 继续保存会话、消息、run、公开事件、部分回答、最终用量和审计；Redis 丢失不得制造第二个 run、第二条消息或虚假成功。
3. 多实例启动、幂等重连、显式停止和浏览器断线均能识别真实执行所有者；只有租约确认过期的孤儿 run 才能被终止。
4. 真实验证流式增量、有限检查点、断线取消、跨实例恢复、依赖故障、跨用户与课程授权隔离。
5. 落实原始消息默认 180 天的可配置清理，以及 `AI_QUESTION_IMAGE` 稳定媒体引用的可靠释放边界。

## 当前缺口与必须修复的失败场景

- `AgentRunCoordinator` 的执行句柄只在单个 JVM 的 `ConcurrentHashMap`。请求重试落到其他实例时只能返回已保存快照，无法判断谁仍持有上游流。
- `recoverOrphanedRuns()` 在实例启动时直接收口全部活动 run。两个 Agent Access 实例并存时，新实例可能把旧实例仍在生成的 run 错误标记为 FAILED。
- MySQL 的同会话活动唯一约束能防止重复 run，但不能限制同一用户在多个会话并发，也不能低成本执行分钟/日额度预留。
- 当前取消主要依赖本实例句柄和一次 Python HTTP 请求；请求落到非执行实例或 Redis/网络短暂故障时，必须仍能留下可被执行实例观察到的取消事实。
- 消息保留与 AI 图片引用释放只有架构约定，尚未形成可验证的有界清理流程。

这些是引入 Redis 租约和短期计数的具体理由；不会新增额外 hash、baseline 或 gate，也不会以 Redis 取代数据库唯一约束和事务。

## 实现边界

### Redis 短期状态

- 所有 Key 使用独立版本化前缀和 Redis DB 6，至少包含：run 执行租约、取消标记、owner 最近 run 元数据、用户活动 run 集合、分钟窗口计数和当日额度预留。
- 获取、续期、token 匹配释放、过期清理和额度预留/回退使用 Redis 原子命令或短小 Lua；释放操作不得删除其他实例续租后的新租约。
- 最近运行缓存只含 runId、conversationId、ownerUserId、状态、最后持久化 sequence、实例标识和到期时间；禁止保存消息正文、回答、提示词、工具原始结果、授权课程正文、媒体 URL、Token 或长期记忆。
- 同一 `clientRequestId` 的幂等重放不重复占并发位或分钟/日额度。最终真实用量仍写 T14.2.2 MySQL 表，Redis 只做开始前预留和短期加速。
- 默认阈值必须配置化；产品尚未确认的生产数值不得写成不可修改常量。测试可使用低阈值稳定覆盖 429、TTL 和恢复。

### MySQL 与多实例运行

- `uk_ai_run_active_conversation`、消息请求唯一约束及事务继续是最终重复写保护。Redis 判断成功后仍必须接受数据库唯一约束裁决。
- 新运行无法访问 Redis 时，在创建新消息/run 前返回 503；不能降级为无限制调用。会话读取、消息读取、已保存事件恢复和幂等取消仍以 MySQL 为准。
- 运行创建成功但租约绑定失败时，必须有界收口为唯一失败/中断终态并释放活动槽；不得留下永不结束的 run。
- 启动恢复改为租约感知：不得终止仍有有效租约的其他实例运行；只有租约过期且数据库仍为活动态时才能用条件更新收口孤儿。
- 非执行实例的重连只重放并有界跟随 MySQL 已持久化事件，不重启 Python；取消写入短期取消标记，执行实例在续租/事件边界观察后停止上游。租约丢失同样阻止后续模型和工具调用。

### SSE、部分回答和真实链路

- Python 仍立即发送 `RUN_ACCEPTED`，按现有 9 类事件连续编号并只发一个 `FINAL_RESULT`。Java 必须先持久化事件和有限 `PARTIAL_CHECKPOINT`，再向浏览器发送。
- 最后一个浏览器连接断开后触发有界取消；已经保存的部分回答标记为中断，恢复只读记录，不自动重新生成或重复扣费。
- 慢客户端、首事件/空闲/总超时、Redis 续租失败和模型/工具取消都必须停止新增工作并产生一个安全终态；不能承诺供应商已接收请求一定不计费。
- 不使用 Redis Stream、Redis Pub/Sub 作为新的事件事实链，不增加 Kafka/RocketMQ，也不让 Python 访问 MySQL。

### 保留期与媒体引用

- 原始消息默认保留 180 天并可配置；清理任务按稳定游标和有界批次运行，不执行全表一次性删除。
- 删除消息正文前保留必要的安全审计、最终用量和聚合记忆事实。部分/完整回答被删除后，恢复接口不得伪造正文。
- `AI_QUESTION_IMAGE` 只保存稳定 mediaId 和消息引用；引用建立/释放复用既有媒体事件信封、Outbox、有限重试和 `eventId` 幂等。不得保存 Bucket、Object Key 或签名 URL，不得直接接 OSS SDK。
- 如需数据库结构，只能从 Agent Access V4 向前新增；严禁修改 V1～V3。没有实际媒体引用时不得制造释放事件。

## 验收要求

1. 自动化覆盖单实例、两个 Agent Access 实例、租约竞争/续期/错误 token 释放、同会话冲突、同用户跨会话并发、分钟/日额度、幂等重放、TTL 回收及 Redis 不可用。
2. 使用两个本地 Java 端口和一个真实 Python Runtime 验证 SSE：收到增量后断开，确认后续模型/工具停止、MySQL 保存部分回答与唯一中断终态；重连另一 Java 实例只恢复已保存事件，不生成第二次 run。
3. 使用一个最小、低成本初中数学请求验证百炼真实文本链；课程候选必须经当前 Course 授权，错误 owner、退课/旧版本或依赖不可用时 fail-closed。不得输出完整提示词、模型回答、Token 或临时 URL到验收日志。
4. 模拟 Redis 错误地址或隔离实例，不停止共享 Redis 服务；验证新运行 503、已保存读取仍可用、活动运行不会伪造成功，恢复后无重复运行。
5. 用明确过期的随机 local/test 消息与媒体引用验证 180 天有界清理和引用释放；临时 MySQL 行、Redis Key、消息、媒体引用及日志文件按稳定 ID 精确清理，不能清空 DB 6 或共享表。
6. 完整执行 Java、Python、OpenAPI/生成客户端回归；不修改 Vue，前端只做生成客户端兼容性检查。

## 数据与清理边界

前置审计没有创建业务测试数据，只执行 Redis PING/DBSIZE 与配置存在性检查。实现验收可在 `edu_platform_agent_dev`、Redis DB 6 和明确 local/test 依赖中创建最小随机 Fixture；交付文档必须逐项记录 owner、conversation/run、Redis 前缀、媒体引用和清理结果。不得操作用途不明数据库、生产前缀或他人数据。
