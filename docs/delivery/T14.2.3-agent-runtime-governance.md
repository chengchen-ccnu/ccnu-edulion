# T14.2.3 Redis 运行治理与 Agent 真实链路交付

日期：2026-09-10。状态：实现、自动化与本地真实链路已通过；PR/CI 状态以本文末尾最新记录为准。

## 目标与功能边界

T14.2.3 在不改变 T14.1/T14.2.2 事实链的前提下，为 `agent-access-service` 增加 Redis 短期运行治理，修复多实例启动误终止他人 run，完成断线取消、跨实例持久事件恢复、180 天原始消息清理和 AI 图片引用释放。

- MySQL 继续是会话、消息、run、SSE 事件、取消、用量、审计与长期记忆的事实源；同会话活动 run 仍由 `uk_ai_run_active_conversation` 裁决。
- Redis 只保存有 TTL 的租约/不可猜 owner token、取消标记、最近 run 安全元数据、用户活动 run ZSet 和分钟/日预留计数。不保存正文、回答、提示词、工具原始结果、课程正文、临时 URL、秘密或长期记忆。
- 跨实例恢复只按有界时长/间隔读 MySQL 已持久事件，不使用 Redis Stream/PubSub，不重启 Python，不增加第二条事件事实链。
- 本任务不实现 Vue、T13.4、T15A/T15B 或自主组题 Skill。

## 主要架构与调用流程

1. 消息 POST 先以 `owner + conversationId + clientRequestId` 查 MySQL 幂等事实；未命中时再用 Redis Lua 原子预留并发位、分钟次数与当日 Token。Redis 不可用或超额都在写消息/run 前返回 503/429。
2. Java 完成题目、课程、Learning 与 AI 图片授权后，在单个 MySQL 事务创建消息/run/媒体绑定 Outbox，再用不可猜 token 原子绑定 Redis 租约。绑定失败时补写唯一 FAILED 终态并释放 MySQL 活动槽。
3. 持有实例每 5 秒续租并在每个事件前复核租约/取消标记。事件先经 MySQL 连续 sequence 条件更新与部分检查点持久，再发给浏览器。失租、Redis 故障、断线或超时都先停止上游，再竞争唯一安全终态。
4. 非持有实例取消先写 2 分钟 Redis 标记；恢复连接只每 250 ms 读取新增 MySQL 事件，最长 30 秒，并从浏览器实际收到的最后 sequence 续读。启动及默认每 15 秒的低频复核，仅对超过两倍租约窗口、Redis 明确无租约且 MySQL 仍活动的 run 做条件终态更新。
5. 消息清理单例游标使用 `(created_at,id)` 稳定顺序，每轮最多 100 条（可配，代码上限 500）。正文与原稳定上下文清空后返回 `contentState=PURGED`；run/事件/用量/审计/归一化记忆保留。实际 BOUND 的 AI 图片在同事务转 RELEASED 并写 Media Outbox。

### 默认 Redis Key 与 TTL

| Key 类型 | 数据结构 | 默认 TTL/窗口 | 内容边界 |
|---|---|---:|---|
| `...:run:{runId}:lease` | String | 15 s，5 s 续租 | 只有不可猜 owner token |
| `...:run:{runId}:cancel` | String | 2 min | 只有取消布尔标记 |
| `...:run:{runId}:meta` | Hash | 24 h | run/conversation/owner ID、状态、sequence、instance、到期时间 |
| `...:user:{owner}:active` | ZSet | 24 h，成员按租约到期清理 | 预留 ID 或 runId 与到期分数 |
| `...:idem:{owner}:{conversation}:{request}` | String | 预留 15 s，绑定后 24 h | 预留 ID 或绑定 runId |
| `...:quota:minute:{owner}:{window}` | String counter | 2 min | 新 run 次数 |
| `...:quota:day:{owner}:{yyyyMMdd}` | String counter | 48 h | 预留 Token |

默认 Key 前缀为 `edu:agent:runtime:v1`，本地使用 Redis DB 6。部署可调默认额度为单用户并发 2、每分钟 10 个新 run、每日预留 200000 Token、每 run 保守预留 8000 Token。这些不是已确认的生产数值，必须按容量/成本评审配置。

### 两实例 + 真实 Python/百炼链路

通过安全包装器启动 Java A `18086`、Java B `18087` 和真实 Python Runtime `8000`，只发送一个最小初中代数请求。验收输出只保留 ID、事件类型、状态与计数，没有完整提示词/回答、Token、API Key、临时 URL 或个人隐私。

- A 从 `RUN_ACCEPTED` 开始，收到首个 `TEXT_DELTA` 后主动断开浏览器响应。Python 记录为仅 1 次 run POST 和 1 次有界 cancel POST。
- MySQL 中该 run 最终为 `CANCELLED`，助手消息为 `PARTIAL`，共保存 32 个连续公开事件，仅 1 个 `FINAL_RESULT`。事件中包含已保存部分文本，不自动重新生成。
- 同一 `clientRequestId` 改从 B 重连，返回同一 runId 并重放 32 个 MySQL 事件/唯一终态；Python 没有新的 run POST，因此未产生第二次模型调用或重复扣费。
- 启动 B 不会无条件终止其他 run；有效租约/真孤儿的精确启动分支由自动化稳定覆盖。已经发给模型供应商的请求可能仍计费，本任务不做反向承诺。
- 另以 Java `18088` 和不存在的 Redis 端口启动隔离故障实例，未停止共享 Redis。新消息返回 503 `AGENT.GOVERNANCE_UNAVAILABLE`，且未写入任何消息/run；故障期间已创建会话的详情和消息列表仍从 MySQL 正常返回。

## 已知风险与后续依赖

- 每 run 日额度是开始前保守预留，最终真实用量仍以 MySQL `ai_usage_record` 为准。生产上线前需确认并发/分钟/日限额、单 run 预留量和是否需按最终用量做另一个可审计结算任务；不应在本任务把未确认值固化。
- Redis 对新 run 是 fail-closed 依赖；短时故障会拒绝新生成，但本人会话/消息/已保存事件与幂等取消仍可读 MySQL。生产 Redis 高可用、过期策略和容量告警由发布/运维任务确认。
- T13.4 仍需提供版本化用户帮助材料与 Help 专家的可授权检索；本任务不伪造帮助内容。
- T15A 可依赖 0.23.1 的 `contentState`、`aiQuestionMediaIds`、原 SSE/恢复/取消语义实现独立 AI 页；必须展示部分/已清理状态，只上传稳定 mediaId，不在浏览器重建租约、额度或长期记忆逻辑。T15B 后续仍需遵循页面规格的普通自主练习浮窗边界。
