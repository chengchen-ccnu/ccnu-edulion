## 诊断证据与实际原因

MySQL 8.0.34、InnoDB、`innodb_force_recovery=0`。用户确认维护窗口并保持暂停写入、导入及其他发布器；脚本实际检查无其他 Learning 数据库连接、无 Learning JVM。所有数据库/带凭据命令通过 `Invoke-WithLocalEnvironment.ps1`，只连接明确 Learning 开发 Schema；未维护其他域。

同一个 REPEATABLE READ、READ ONLY 一致快照的初始结果：

| 口径 | 实际结果 |
|---|---:|
| PRIMARY PUBLISHED / FAILED / PENDING | 5,734 / 6,896 / 0 |
| 二级索引 PUBLISHED / FAILED / PENDING | 5,734 / 6,896 / 1 |
| PRIMARY / 二级索引总数 | 12,630 / 12,631 |
| 二级键与 PRIMARY 状态/时间不一致 | 1 |
| 异常键对应 PRIMARY 状态 / attempts | FAILED / 318,824 |

EXPLAIN 确认 PRIMARY 全表扫描、二级覆盖计数及生产查询的 index condition/filesort。关闭会话级 ICP 后覆盖索引仍为 PENDING=1，非覆盖待发查询不再返回该 FAILED 行；开启时返回 FAILED/318,824。同一视图排除并发影响，执行计划排除访问路径误判。实际故障是待发二级索引多出一个陈旧 PENDING 键，ICP 可据此领取已经 FAILED 的主键行；这解释反复领取机制，不证明所有 318,824 次尝试均由该异常造成。

历史引擎日志中，2026-08-19 有64条 MY-011971，提示表空间250的页 LSN 超过当时系统 redo LSN；另有 MY-012869，记录该待发索引更新找不到键。初次只读页头归属为 PRIMARY58/二级4/管理页2，因而先暂停修复并报告，不直接假定仅二级索引异常。历史时间按数据库记录显示，未擅自转换时区。

用户随后授权恢复调查和受保护备份验证。当前全部主键数据可导出、恢复、逐列一致；在本表导出锁下取得的物理副本通过离线页校验和检查。源表 CHECK TABLE 只报告待发索引12631条、应为12630条，未报告当前主键错误。这些当前检查支持最小二级索引维护，不能证明历史上从未发生数据丢失。

**现存索引故障已确定并修复；物理形成原因仍未查明。** 历史 LSN/redo 不一致是恢复风险证据，不能据此断言复制数据文件、日志缺失、磁盘故障或 MySQL 缺陷中的某一项。初次历史页归属不保证当时页归属完全相同（页可能复用）。未取得历史完整事件清单或当时系统恢复操作记录。

4. 在已验证备份后执行源表 CHECK TABLE。它报告二级条目数量不符，并将异常索引标记不可用（后续该索引查询1712）；PRIMARY仍可读取。此副作用按 [MySQL CHECK TABLE说明](https://dev.mysql.com/doc/refman/8.0/en/check-table.html) 记录。
5. 最初同一 ALTER 中 DROP/ADD 同定义索引未实际更换 indexId，检查仍失败，未记为修复成功。随后在维护窗口分两条执行下方原索引重建，显式 INPLACE/EXCLUSIVE，禁止回退全表 COPY。失败时不覆盖源表或改状态。

```sql
ALTER TABLE learning_outbox_event
  DROP INDEX idx_learning_outbox_pending, ALGORITHM=INPLACE, LOCK=EXCLUSIVE;
ALTER TABLE learning_outbox_event
  ADD INDEX idx_learning_outbox_pending(status,next_attempt_at,occurred_at),
  ALGORITHM=INPLACE, LOCK=EXCLUSIVE;
```

修复后原名称和定义完全相同，SHOW CREATE TABLE 原值相同；PRIMARY indexId=600/rootPage=4保持，二级 indexId从601更换为3394。源表 CHECK TABLE 返回 OK。主键/二级状态、总数和键值一致，PENDING均0；执行计划仍使用原待发索引。

维护前、维护后及真实回归清理后均与恢复备份比较全部15列与双向 ID 集合，差异0：事件 ID、正文、status、attempts、错误、所有时间均保留。没有修改 V1 或新增 Flyway，没有批量改状态、自动重放或队列 purge；6,896条历史 FAILED 和异常行318,824次尝试保留。

## 真实批量发布与消费回归

`T1640LearningOutboxRealAcceptanceTest` 直接使用真实 MySQL Repository、RabbitMQ、生产 Publisher/Listener/Processor/容器，不启动后台 Spring 调度或其他服务。发布入口始终为 `publishPending()`，没有调用指定 ID 的 `publish(event)`。

每轮仅五条随机合法 QuestionImportRequested v1信封、一个零行 COMPLETED 导入任务、随机独立 exchange 和两个 durable 队列：

| 场景 | 实际验证 |
|---|---|
| 同批 ACK成功与失败隔离 | 成功事件PUBLISHED；return/NACK不阻断其他事件 |
| mandatory return后恢复 | 首次PENDING/attempts1，新增本轮精确绑定，到期后PUBLISHED |
| unroutable return耗尽 | 约2秒/4秒真实退避，三次后FAILED、错误留痕 |
| Broker真实NACK | 本轮队列容量1、reject-publish，预填一条测试消息，收到至少3次NACK；三次后FAILED |
| 到期后不自动重放FAILED | 等待耗尽事件的下次尝试时间（约8秒）真正到期，再运行生产批量扫描；状态/次数/NACK数量不变 |
| 未来事件 | 未到期事件一直PENDING/attempts0，最终精确删除 |
| 真实重复运输/幂等消费 | Broker投递三次（两种eventId，其中一种重复），生产AUTO ACK容器/消费者只新增两条消费事实 |

终态导入任务用于生产 eventId 幂等分支；未重做导入或下载媒体。Parser/QuestionService/MediaClient 为未调用的测试替身并验证零交互；不能把本专项当作真实媒体导入验收。真实 Publisher 参数在测试中设置上限3，生产默认20未改。按微秒范围验证退避，不改 next_attempt_at 加速。

首轮 RabbitMQ拒绝非持久、非独占临时队列，测试在创建任务/事件前失败；改用本轮 durable拓扑后通过。随后补充“FAILED真正到期后仍不重放”并完整复跑，最终1项通过、0失败/错误/跳过。未通过轮不计为成功。
