## 3. 已确认产品边界

- 普通账号只允许学生、学生＋教师、封禁三种组合；禁止仅教师。管理员独立、同权，不得拥有学习/教学能力，不得报名、公开注册或申请教师。普通能力命令不能产生管理员。
- 首次教学授予只能经审核；恢复教学能力必须有有效的历史通过事实。撤权保留学生身份、审核决定与批准材料，封禁保留领域数据。高风险命令有原因、影响说明、明确确认及审计，revision/409 防覆盖，稳定请求标识支持幂等。
- 首位正式管理员走受控初始化；后续由当前有效管理员向邮箱发送一次性邀请，邮箱所有者验证并自行设密码。现有本地管理员可作为测试起点。禁止自动把普通学生/教师账号转换成管理员；与既有身份冲突时先在契约评审中明确拒绝/处理规则，不静默迁移领域归属。
- 管理员不能封禁自己、不能停用最后一名可用管理员。多人同时操作必须以数据库并发约束保证，不以“先查人数再更新”或前端按钮隐藏代替。
- 正确账号及密码后，封禁账号才得到可理解的封禁与联系管理员提示；未知身份和错误密码仍统一失败。旧登录设备失效，支持邮箱由部署配置提供，不泄露教师审核原因。
- 撤权或封禁教师，暂停所有当前已发布课程；仅恢复同一撤权周期系统暂停的课程，不恢复原来下架/草稿/归档课程。保留报名、进度、答题、草稿与成绩。沿用 T16.1 的服务端准入边界和既有短期 OSS 授权有效期，不承诺取消已经签发的 URL。
- 最终规则为暂停停止 HOMEWORK/EXAM 计时和结算，恢复按实际暂停区间顺延未完成任务/草稿；已关闭、提交、批改事实不变。不得退回早期“恢复立即判缺交”的旧方案。
- T16.4 才投递站内消息，T17C 才做管理端页面。T16.3 只提供必要可靠事实/事件，不创建通知页面、课程审核、管理员等级、用户注销或全站账号迁移。

## 4. 必须覆盖的失败场景

### 4.1 旧会话缓存回填竞争

现有登录/刷新读取用户后无条件回填 Redis 会话版本；禁用事务删除缓存与数据库提交并非一个原子动作。并发请求可能读取旧版本，在缓存删除后重新写回旧值，使 Gateway 再接受旧 JWT。只增加版本号但不处理发布顺序与并发读写，不能解决此场景。

实现需复用数据库锁/事务及必要 Redis 原子更新，明确提交成功、缓存发布失败、并发登录/刷新、Redis 故障与恢复的拒绝/重试语义；避免把未提交的新能力提前当作已生效。验收必须真实并发复现并验证修复，不只顺序调用“禁用→旧 Token”。不在本审计指定第二套会话存储或额外 hash/gate。

### 4.2 权限事实与课程暂停跨服务失败

IAM 与 Course 无跨库事务。需要持久化待执行命令及明确的当前应用状态，使用同一 accessRevision/suspensionId 有限重放，不能靠内存队列或单次 HTTP 调用。HTTP 超时可能已在 Course 生效，重放不能创建第二段暂停或重复补时；过期命令不能覆盖新恢复。

契约须区分 IAM 决定已提交、课程协调待完成/失败/已应用，不能把尚未应用的暂停假称端到端成功。明确确认前后权限再次变化、Course 不可用及恢复期间的访问边界，按现有 T16.1 行为实测；不能因通知或协调失败静默回滚已提交的资格事实，也不能为恢复放开访问门禁。复用现有 Outbox/有限补偿，跨服务事件继续 confirm/return/有限重试/死信与 eventId 幂等，不造通用工作流平台。

### 4.3 管理员保护与邀请

- 两个管理员并发停用对方，不能出现最后一个管理员也被停用；并发权限命令、刷新和旧管理 JWT 的权限必须再次校验。
- 邀请令牌不得进入日志、URL 预览或可读取的管理列表；验证邮箱所有权、有效期、一次消费、重放和密码校验。若新增摘要存储等安全措施，应说明其保护邀请凭证的具体风险，不增加无消费者的 hash/manifest/baseline。
- 发送失败不等于邀请已经送达；重试不重复创建管理员。发送、接受、账号创建及审计的事务/重试边界必须清楚；未经邀请的注册永远不能产生管理员。
- 邮箱身份冲突、已存在管理员、过期/已使用邀请、错主体、旧权限、401/403/404/409/422/429 和不可枚举错误需明确定义；接受邀请的公共入口只能精确放行，不能公开整个 admin 路由。
