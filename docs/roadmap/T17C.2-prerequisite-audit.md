# T17C.2 账号权限管理前端前置审计

> 2026-10-04 总控；最新 main `db255c2`（PR #88）。本次只记录真实审计、状态和建议，不实现页面、后端、OpenAPI或迁移。结论：现有业务规则与环境基本齐备，但命令恢复查询契约不足，暂不准备 `codex/t17c2-account-permissions-web`。

## 1. 已具备的基础

- T16.1～T16.3 与 T17C.1 已合并。管理端已有稳定应用壳、唯一统一身份入口、两项侧栏和真实教师审核；账号权限仍保持建设中，不能先启用空页面。T17C.2 使用 `/admin/users`，不实现邀请/受邀开户或复制教师审核。
- OpenAPI 0.31.0 与生成客户端已有账号分页/详情（AdminUser）、权限影响预览、四种受控命令、按 commandId 查询及有限补偿。审核不可替代第一次资格授予；ADMIN独立身份，不提供任意角色编辑器。
- 本轮T17C.1独立验收实际启动Gateway/IAM/Course/Media/Learning/Operation、MySQL/Redis/RabbitMQ并完成真实长链。安全包装器复核IAM/Course/Learning专用dev Schema、JWT及Course协调秘密配置存在，未输出值。前置历史迁移为IAM V5、Course V7、Learning V21，Media V6、Operation V2；本轮未新增迁移。验收结束相关Java/前端均已停止，实施时需重新启动。
- T17C.2自身不新增图片上传，不要求OSS、模型/Agent、Qdrant、Neo4j、FFmpeg或SMTP。当前OSS默认端口CORS限制不阻断账号命令；若复用资质Fixture，仍须使用已授权origin或由用户正确配置CORS，不能关闭浏览器安全。

## 2. 已审查的行为边界

| 接口/实现 | 可消费事实与限制 |
|---|---|
| GET `/api/v1/admin/users`、`/{userId}` | page/size、keyword/status及脱敏身份、能力、封禁/短期锁定、revision；无角色筛选/任意排序契约，也没有最新权限命令字段。身份关键词只能在页面内存，不放URL/持久存储/日志；列表不得再逐行读取详情 |
| POST `/{userId}/permission-previews` | 服务端核对动作、历史APPROVED及当前状态，真实读取Course范围和Learning去重ACTIVE人数；依赖失败503，不假定零影响。五分钟预览，确认时再校验影响/revision |
| POST `/{userId}/permission-commands` | REVOKE_TEACHING / RESTORE_TEACHING / BAN / UNBAN，理由10～500字、二次确认、稳定ID及原载荷；202只表示IAM提交。自封禁/最后管理员保护、旧会话失效、首次教学不能绕过审核 |
| GET `/permission-commands/{commandId}` | 仅知道命令ID时可查当前安全事实。NOT_REQUIRED/PENDING/FAILED/APPLIED不混为成功；APPLIED仅Course事实/Outbox确认，不表示所有Learning消费者或消息都完成 |
| POST `/{commandId}/retry` | FAILED且当前attempts小于6，expectedAttempts防并发；自动最多3次、显式补偿最多再3次，每次增加一次预算，不新建周期 |

普通UNBAN只恢复STUDENT；恢复教学需独立RESTORE_TEACHING且有历史批准，Course确认前不授回TEACHER，确认后账号revision可能再次增加，前端须重读详情。旧disable接口已废弃并返回409，不可绕过预览；“登录失败锁定”不等于“账号封禁”，不能把unlock当UNBAN。

## 3. 阻断：跨页面命令恢复

具体失败场景：管理员提交撤权，IAM决定已持久化，但HTTP响应丢失；随后浏览器关闭/崩溃，或另一管理员接手。Course协调最终FAILED，账号后续预览/变更因 `IAM.COORDINATION_PENDING` 被拒绝。管理员仅知道userId，却没有公开接口找到原commandId，因此无法查询状态或调用已有有限补偿。

证据：

- `docs/api/openapi.yaml` 的 AdminUser不含command定位字段；权限命令集合只有POST，GET/补偿路径均要求commandId。未找到按账号查询命令的公开路径。
- `AccountPermissionController`仅preview/change/get-by-id/retry。`AccountPermissionService.validate`在同账号存在PENDING/FAILED命令时阻止新动作。
- 当前实现把clientRequestId作为command主键，但OpenAPI并未保证两个ID相等，前端不能依赖该内部偶合；另一管理员也不拥有原clientRequestId。
- 数据库主键、事务、幂等及审计已经可靠保留事实，但没有授权读取入口；Git、版本号、类型和普通测试不能让重新进入页面的管理员取得命令。此处需要的是一个最小查询，不是新hash、gate、缓存或第二套审计。

本次为代码/契约审计确认，**未主动撤销现有教师或制造真实FAILED命令**。不把静态分析写成真实故障复现，也不通过读IAM表为前端补足接口。

## 4. 建议补口（待用户确认，不是已发布契约）

优先独立补一个“按目标userId读取最近权限命令”的只读接口，复用现有 `AccountPermissionCommand`。例如 GET `/api/v1/admin/users/{userId}/permission-commands/latest`：当前有效管理员授权，存在事实返回200；账号存在但没有命令返回204；账号不存在404。具体路径和空值语义在后端任务先评审OpenAPI、向前升级并生成客户端后再实施，前端不得提前猜用。

- 最近顺序须确定，例如账号决定revision降序，并加稳定次序；命令跨操作者可读，但仍只限当前有效管理员。返回不得包含理由、请求JSON、联系方式、凭据或内部响应正文。
- 不只返回FAILED，也可找回最近已完成事实，便于未知结果后核对；仍由既有服务端决定是否允许补偿，查询不创建命令、不消耗预算、不触发Course写入。
- 不要求全量历史页、第二套DTO、通用任务系统、新MQ/Redis或数据库表。既有user_id索引可先评估；确有查询性能证据才向前增索引，不改V5。
- 验收：无记录、未知账号、非管理员/失效管理员、两管理员接手、PENDING/FAILED/APPLIED/NOT_REQUIRED、多命令确定排序、响应丢失后重新查询、既有补偿预算及并发409不变、生成客户端/Mock同契约。

补口合并后，总控重新审计并从最新main准备T17C.2前端分支。本次没有擅自创建该后端实施分支或修改业务范围；建议需要用户确认。

## 5. 后续前端验收要求

页面保持账号分页与按需详情，page/status/userId及返回的commandId可以作有界URL定位；身份关键词、理由和写入载荷仅内存。刷新/另一个管理员接手先重读账号与最近命令，不能用页面按钮状态推断实际权限。

预览展示影响课程/去重学生人数与有效期，二次确认后以稳定原载荷提交；409明确刷新核对，503/超时未知结果保留离页保护并有限重试，不自动新建命令。PENDING低频、有界、可取消查询；FAILED仅在服务器次数允许时明确补偿，达到上限说明需后续运维处理，不能无限循环。401/403清私有数据和旧请求；卸载停止请求/计时器。

真实闭环必须使用最小临时已审核普通账号与至少两名临时管理员，验证撤权→课程暂停→恢复及只恢复原周期、BAN/UNBAN、原会话失效、自封禁/最后管理员保护、并发409与两管理员接手。不得操作唯一原管理员或手工《线性代数》；全部临时事实精确清理，不purge/FLUSHDB或全表删除。还需360/768/1440、键盘、深链接/刷新/返回及完整错误状态，独立交付记录、中文注释与实际测试结果。
